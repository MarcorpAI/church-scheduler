# ServeFlow — Technical Specification

**Task Scheduling & Coordination for Church Services**
Version 1.0 | February 2026 | Weekend Build Sprint

---

## 1. Project Overview

ServeFlow is a web application that enables church coordinators to schedule services, assign tasks to volunteers, and track completion in real time. This spec is scoped for a weekend build with a focus on shipping a functional MVP.

---

## 2. Tech Stack

| Layer | Technology | Rationale |
|-------|-----------|-----------|
| Frontend | Next.js 14 (App Router) | Full-stack framework, fast iteration, built-in API routes |
| UI | Tailwind CSS + shadcn/ui | Rapid, consistent UI with pre-built accessible components |
| Backend / API | Next.js API Routes + Server Actions | Co-located with frontend, no separate server needed |
| Database | PostgreSQL (via Supabase) | Managed Postgres with built-in auth, real-time, and storage |
| ORM | Prisma | Type-safe queries, easy migrations, great DX |
| Auth | Supabase Auth (or NextAuth.js) | Email/password auth with role management out of the box |
| Real-time | Supabase Realtime (Postgres changes) | WebSocket-based subscriptions on DB changes for live updates |
| Email | Resend | Simple transactional email API, generous free tier |
| Hosting | Vercel | Zero-config Next.js deployment, preview URLs per branch |
| Cron / Scheduling | Vercel Cron (or QStash by Upstash) | Trigger scheduled reminders without a separate worker |

## 3. Data Model

All tables include standard `id`, `created_at`, and `updated_at` fields.

### 3.1 Users

| Field | Type | Notes |
|-------|------|-------|
| id | UUID (PK) | Generated by Supabase Auth |
| email | String (unique) | Login credential |
| name | String | Display name |
| role | Enum: `ADMIN` \| `VOLUNTEER` | Controls access level |
| avatar_url | String (nullable) | Optional profile image |

### 3.2 Services

| Field | Type | Notes |
|-------|------|-------|
| id | UUID (PK) | Auto-generated |
| name | String | e.g. "Sunday Morning Service" |
| description | Text (nullable) | Optional details |
| date | DateTime | Service date and start time |
| recurrence | Enum: `NONE` \| `WEEKLY` \| `MONTHLY` | Recurrence pattern |
| created_by | UUID (FK → Users) | Admin who created the service |

### 3.3 Tasks

| Field | Type | Notes |
|-------|------|-------|
| id | UUID (PK) | Auto-generated |
| title | String | e.g. "Set up projector" |
| description | Text (nullable) | Additional instructions |
| status | Enum: `PENDING` \| `IN_PROGRESS` \| `COMPLETED` | Current state |
| service_id | UUID (FK → Services) | Parent service |
| assigned_to | UUID (FK → Users, nullable) | Assigned volunteer |
| due_time | DateTime (nullable) | Optional deadline within the service |

### 3.4 Notifications

| Field | Type | Notes |
|-------|------|-------|
| id | UUID (PK) | Auto-generated |
| user_id | UUID (FK → Users) | Recipient |
| type | Enum: `TASK_ASSIGNED` \| `STATUS_CHANGE` \| `SERVICE_REMINDER` | Notification category |
| title | String | Short summary |
| message | Text | Full notification body |
| read | Boolean (default false) | Read/unread state |
| reference_id | UUID (nullable) | Links to related task or service |

### 3.5 Entity Relationships

- A **User** can be assigned to many **Tasks** (one-to-many)
- A **Service** has many **Tasks** (one-to-many)
- A **User** has many **Notifications** (one-to-many)
- A **Service** is created by one **User/Admin** (many-to-one)

## 4. API Design

All endpoints are implemented as Next.js API routes under `/api`. Authentication is enforced via middleware that validates Supabase session tokens. Admin-only routes check the user role before proceeding.

### 4.1 Auth Endpoints

| Method | Route | Description | Access |
|--------|-------|-------------|--------|
| POST | `/api/auth/signup` | Register new user (defaults to VOLUNTEER) | Public |
| POST | `/api/auth/login` | Email + password login | Public |
| POST | `/api/auth/logout` | End session | Authenticated |

### 4.2 Service Endpoints

| Method | Route | Description | Access |
|--------|-------|-------------|--------|
| GET | `/api/services` | List all services (with filters for date range) | Authenticated |
| POST | `/api/services` | Create a new service | Admin |
| GET | `/api/services/:id` | Get service detail with tasks | Authenticated |
| PUT | `/api/services/:id` | Update service | Admin |
| DELETE | `/api/services/:id` | Delete service and its tasks | Admin |

### 4.3 Task Endpoints

| Method | Route | Description | Access |
|--------|-------|-------------|--------|
| POST | `/api/services/:id/tasks` | Create task under a service | Admin |
| PUT | `/api/tasks/:id` | Update task (title, description, assignee) | Admin |
| PATCH | `/api/tasks/:id/status` | Update task status only | Assigned user or Admin |
| DELETE | `/api/tasks/:id` | Delete a task | Admin |
| GET | `/api/my-tasks` | Get current user's assigned tasks | Authenticated |

### 4.4 Notification Endpoints

| Method | Route | Description | Access |
|--------|-------|-------------|--------|
| GET | `/api/notifications` | Get current user's notifications | Authenticated |
| PATCH | `/api/notifications/:id/read` | Mark notification as read | Owner |
| PATCH | `/api/notifications/read-all` | Mark all as read | Authenticated |

## 5. Real-Time Architecture

Real-time updates are powered by Supabase Realtime, which listens for Postgres row-level changes and pushes them to connected clients via WebSockets.

### 5.1 Subscriptions

- **Task status changes:** Volunteers and admins subscribed to a service receive instant updates when any task status changes.
- **New notifications:** Each user subscribes to their notifications table row inserts for the bell icon / feed.
- **Service updates:** If an admin modifies a service, subscribed users see changes reflected immediately.

### 5.2 Implementation Approach

On the client, use the Supabase JS client to subscribe to specific table channels filtered by `service_id` or `user_id`. When a change event fires, update the local React state (or use SWR/React Query cache invalidation) to re-render the UI without a full page reload.

## 6. Notification System

### 6.1 In-App Notifications

- Stored in the `notifications` table and delivered via Supabase Realtime subscriptions.
- Displayed as a notification bell with unread count badge in the app header.
- Clicking opens a dropdown/panel showing recent notifications with read/unread state.

### 6.2 Email Notifications

- Sent via Resend when a task is assigned or a service reminder is triggered.
- Keep emails simple and action-oriented with a direct link back to the app.
- Templates: Task Assignment, Service Reminder (X hours before), and Task Completion (admin summary).

### 6.3 Scheduled Reminders

Use Vercel Cron Jobs (cron expressions in `vercel.json`) to run a function every hour that checks for services starting within the configured reminder window (e.g. 2 hours). For each upcoming service, create in-app notifications and send emails to assigned volunteers with incomplete tasks.

## 7. Auth & Authorization

### 7.1 Authentication Flow

- Supabase Auth handles signup, login, and session management with secure HTTP-only cookies.
- Next.js middleware checks the session on every request to protected routes.
- Unauthenticated users are redirected to `/login`.

### 7.2 Role-Based Access Control

| Action | Admin | Volunteer |
|--------|-------|-----------|
| Create/edit/delete services | ✓ | ✗ |
| Create/edit/delete tasks | ✓ | ✗ |
| Assign volunteers to tasks | ✓ | ✗ |
| View all services and tasks | ✓ | ✓ (assigned only) |
| Update task status | ✓ | ✓ (own tasks only) |
| View notifications | ✓ | ✓ |

### 7.3 Row-Level Security

Supabase RLS policies enforce that volunteers can only read services they have tasks in, and can only update the `status` field on tasks assigned to them. Admin users bypass volunteer restrictions via a role check in the policy.

## 8. Key Screens & UI

### 8.1 Login Page

Minimal form with email and password fields. Link to signup. Error handling for invalid credentials.

### 8.2 Admin Dashboard

- Overview of upcoming services with task completion percentages.
- Quick-create button for new services.
- List of recent services sortable by date, with status indicators (all tasks done, in progress, etc.).

### 8.3 Service Detail Page (Admin)

- Service metadata (name, date, recurrence) with inline edit.
- Task list with status badges, assigned volunteer names, and actions to add/edit/reassign/delete tasks.
- Volunteer assignment via a searchable dropdown of registered users.

### 8.4 Volunteer Dashboard

- Today's tasks prominently displayed at the top.
- Upcoming tasks grouped by service.
- Each task card shows title, service name, time, and a status toggle (Pending → In Progress → Completed).

### 8.5 Notifications Panel

Slide-out panel or dropdown triggered by the bell icon. Shows recent notifications with timestamps, read/unread styling, and links to the relevant service or task.

## 12. Key Technical Decisions

**Supabase over standalone Postgres + custom auth:** Supabase bundles auth, database, and real-time into one managed service. This dramatically reduces setup time for a weekend sprint without sacrificing flexibility.

**Prisma alongside Supabase:** While Supabase has its own JS client for queries, Prisma provides type-safe, auto-completed database access and straightforward migrations. Use Prisma for CRUD operations and Supabase client for auth and real-time subscriptions.

**Server Actions for mutations:** Next.js Server Actions allow form submissions to call server-side code directly, reducing boilerplate compared to separate API routes for simple create/update operations.

**Vercel Cron over background workers:** For the MVP, a cron endpoint that runs every hour is sufficient for service reminders. This avoids setting up a separate queue or worker infrastructure.

**No WebSocket server needed:** Supabase Realtime handles all WebSocket connections. The app just subscribes to database changes on the client side.

## 13. MVP Scope Boundaries

### In Scope

- Email/password authentication with two roles (Admin and Volunteer).
- Full CRUD for services and tasks.
- Task assignment and status tracking with real-time updates.
- In-app notifications with read/unread state.
- Email notifications for task assignments and service reminders.
- Mobile-responsive UI.

### Out of Scope (Post-MVP)

- Multi-church / multi-organization support.
- WhatsApp, SMS, or push notifications.
- Chat or messaging between users.
- Advanced analytics or reporting dashboards.
- Calendar integrations (Google Calendar, etc.).
- Task templates or recurring task auto-generation.
- Offline mode / PWA.

## 14. Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Real-time complexity delays other features | High | Implement real-time last; MVP works without it via polling/refresh |
| Email delivery issues (spam, delays) | Medium | Use Resend with verified domain; keep emails simple and transactional |
| Supabase free tier limits | Low | Free tier supports 50K monthly active users and 500MB DB; plenty for MVP |
| Scope creep during weekend sprint | High | Stick strictly to this spec; track nice-to-haves in a backlog, not in code |
